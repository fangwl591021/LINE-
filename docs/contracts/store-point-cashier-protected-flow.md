# 店家點數收銀保護流程

日期：2026-07-09

## 2026-09-20 使用者批准新增扣點用戶

- 新增獨立 `redeem` 角色（扣點用戶），只允許會員查詢、既有消費折抵、收銀通道、本人查單／紀錄。
- 必須驗證 LINE Token；不允許身份 fallback，不開放贈點、商品管理及其他 manager API。
- 只接受 `mode=redeem`，拒絕任何 rewardPoints 欄位、商品模式及自動綁定贈點路徑；原本金額及折抵點數驗證不變。
- 只有管理員角色編輯器能授予或解除；個人資料保存不能取得、撤除或升級此權限。後端交易送出前與真正寫入前重查扣點角色。
- 前端只顯示扣點入口；手機／QR 都沿用收銀流程，電話不可誤入電話贈點 POP。
- 不更動既有身份歸屬、帳本、防重邊界、180 秒通道及店長／贈點用戶規則。

## 2026-09-13 使用者批准新增贈點用戶

- CRM 新增獨立 `reward` 角色；僅會員錢包 QR 查詢、既有消費贈點、本人查單／收銀紀錄，不授予店長管理或扣點權限。
- 新角色必須使用已驗證 LINE Token，不使用 D1 身份 fallback。後端拒絕電話／手動 UID 查詢入口、商品折抵、redeem 及非零扣點。
- 新增獨立 180 秒掃碼查詢 receipt，綁定操作者及 canonical 顧客，KV 僅存 token 雜湊；在 wallet handler 前及原 beforeWrite 邊界重查角色／憑證。receipt 不保證實體相機來源、不作 KV 原子鎖。
- 原 cashierSessionId、舊角色預備／查詢／fallback、消費計算與 requestId 防重均不改；已完成交易仍可用原編號查回，不因 receipt 過期而重贈。
- 正式角色異動與真實贈點未在本機測試中執行；使用者後續已授權此版本提交及部署。

## 2026-09-10 使用者批准補強

### 2026-09-10 使用者同意本人商品動態 QR（待部署）

- 會員明確點選「出示本人 QR」後產生 5 分鐘隨機憑證；D1 只存 SHA-256，QR 不含 UID。身分由驗證後的 authenticatedUserId 解析，不接受代指定 customerUserId。
- 每會員每商品保留一個最新憑證，更新使舊碼失效。匿名只可看商品，產碼須登入；前端不自動背景大量產碼。
- 僅商品所屬店家查驗，掃碼不扣點；確認頁自動載入會員名稱與餘額，不要求手填 UID。送出仍須明確確認點數。
- 送出重查會員映射、商品、期限，原子標記憑證已使用，再進既有防重複交易邊界；未知結果不得重扣或自動恢復憑證。同交易編號查回既有結果。
- 舊靜態商品碼保留相容入口，須另確認顧客；一般收銀及共用母站錢包规则不變。短效碼為持有者憑證，請勿轉傳，店家仍須核對顧客。
- 發布先套用 0032_store_member_product_qr.sql，再 Worker，最後前端；本機測試不代表正式扣點已驗證。

### 2026-09-10 使用者同意商品掃碼分流

會員收銀機相機、相簿及貼上查詢皆先辨識商品碼與客戶碼。可信 LIFF／本站商品網址只取商品 UUID 開啟既有商品扣抵入口，由後端重查店家權限；不得當成客戶查詢。未知網址明確拒絕，過期客戶回應不得回填。客戶查詢、扣點規則、session 及交易防重送機制不變。

送出前持久化交易編號；同編號不同內容拒絕，相同內容查回原結果。D1 唯一約束鎖定顧客未完成的收銀交易。母站結果未知不得自動重扣或解鎖；查單僅原操作者可讀。新交易重查母站餘額，不重用舊交易的餘額；180 秒通道建立和查詢本身不改。商品碼僅帶商品 ID，後端重查店家歸屬、上下架、版本、價格及折抵上限。

本文件記錄目前已驗證速度可接受的店家點數收銀流程。此流程屬於受保護流程，後續除非使用者明確同意，不得修改、重構或順手調整。

## 保護範圍

以下流程不可任意改動：

- 店家手動搜尋客戶帳號。
- 店家掃描 QR 查詢客戶帳號。
- 查到客戶後建立短期收銀點數通道。
- 店家輸入消費金額、折抵點數或贈點資料。
- 店家送出贈點、扣點或消費折抵。

此保護範圍只包含點數收銀，不包含名片、影音名片、按讚、AI 名片夾或其他功能。

## 固定流程

1. 店家以手動搜尋或 QR 掃描找到客戶。
2. 系統在查到客戶時，立即準備點數收銀通道。
3. 收銀通道有效時間為 180 秒。
4. 店家輸入資料期間，系統已先準備：
   - 客戶點數身份。
   - 客戶目前點數來源。
   - 店家操作身份。
   - 店家免費操作狀態。
   - 母站會員與點數狀態是否已可用。
5. 店家送出時，若收銀通道仍有效，應使用已準備好的資料，避免重複查詢。
6. 若收銀通道不存在、過期或驗證不一致，才回到原本安全查詢流程。

## 不可破壞規則

- 不得讓前端自行決定最終點數餘額。
- 不得把查詢失敗顯示為 0 後寫回。
- 不得因為母站短暫查詢慢，就阻止已可辨識的子站客戶使用必要流程。
- 不得把此流程和名片、影音、按讚邏輯混在一起修改。
- 不得在送出階段重複執行已於查詢階段準備完成的母站會員建檔確認，除非收銀通道失效。
- 不得移除安全 fallback。通道失效時必須能回到原本完整查詢。

## 目前實作契約

後端：

- 查詢客戶時建立短期 `cashierSessionId`。
- `cashierSessionId` 儲存在 `ACTMASTER_KV`，有效 180 秒。
- 送出贈扣點時帶入 `cashierSessionId`。
- 若 session 驗證通過，送出流程可重用已準備好的客戶與店家點數資料。
- 若 session 驗證失敗，送出流程必須走舊有完整查詢路徑。

前端：

- 客戶查詢成功後保留 `cashierSessionId`。
- 店家送出贈扣點或折抵時一併傳送 `cashierSessionId`。
- 送出後不可等待非必要刷新才解除按鈕狀態。

## 回歸檢查

任何經使用者同意後的點數收銀修改，都必須至少檢查：

- 手動搜尋找到客戶後可送點。
- 掃 QR 找到客戶後可送點。
- 客戶沒有點數通前仍能被辨識，不應直接中斷必要流程。
- 母站會員已存在時，不應重複拖慢送出。
- 通道過期後仍可 fallback 成功或顯示明確錯誤。
- 店家操作免費，不扣操作者點數。
- 消費折抵仍寫入明細。
- 不影響名片、影音名片、按讚與我的名片觸發。

## 修改限制

本文件是保護契約。後續若要修改以下任一項，必須先取得使用者明確同意：

- `cashierSessionId` 的建立時機。
- 收銀通道有效時間。
- 查詢階段預先準備的點數資料。
- 送出階段重用 session 的條件。
- 母站會員建檔與點數查詢的執行順序。
- 點數收銀 fallback 行為。
