# 名片按鈕與網址契約

本文件定義名片按鈕欄位、格式校驗與儲存規則。

## 欄位

每個按鈕至少包含：

- `label`
- `type`
- `value`
- `color`
- `order`
- `enabled`

建議類型：

- `url`
- `phone`
- `email`
- `line`
- `map`

## 自動正規化

### 電話

輸入電話時，系統應自動轉成：

```text
tel:<phone>
```

允許：

- 台灣手機。
- 市話。
- `+886`、`886`、`86` 等國碼。
- 空格與破折號輸入後正規化。

禁止：

- 無法辨識的電話不得儲存為電話按鈕。

### Email

輸入 email 時，系統應自動轉成：

```text
mailto:<email>
```

禁止：

- 不合法 email 不得儲存。

2026-10-21 Email點擊流程：

- 儲存及網頁名片仍使用mailto:<email>，不批次修改資料或版本設定。
- 新產生的LINE Flex Email按鈕必須是HTTPS寄信頁URI action，不能再把電子郵件標籤接到clipboard action；前後端Flex使用同一共用規則。
- 收件人放寄信頁URL fragment，不傳UID、token或名片ID；寄信頁只解析單一合法to，拒絕CRLF、BCC／Subject參數、腳本及外部轉址注入，不接受任意導向網址。
- 寄信頁主要操作為開啟郵件App（mailto），另提供Gmail與Outlook網頁撰信；只帶入收件人，不寄出、不登入、不自動複製、不寫正式資料。複製是明確點選的次要備援，失敗時可手動選取。
- 需有可見返回／關閉路徑。不能偵測或保證手機已安裝預設郵件App，不把開啟動作宣稱為信件已寄出。
- 舊LINE訊息內容不能回溯更改；需重新產生／分享名片才會使用新按鈕，不自動重送。

### 網址

網址必須是：

```text
https://...
http://...
```

允許：

- 一般網站。
- Google Maps。
- LINE 加好友連結。

禁止：

- 空白網址。
- 無協議的網址直接儲存。
- `javascript:`、不明 scheme。

### LINE 連結

允許：

- `https://line.me/...`
- `https://lin.ee/...`

不建議：

- 未確認用途的 LIFF deep link。

## AI 修正

AI 可以協助修正格式，但不得靜默寫入高風險欄位。

允許：

- 提示「偵測到電話，已轉為 tel:」。
- 提示「偵測到 email，已轉為 mailto:」。
- 建議補上 `https://`。

禁止：

- 自動改姓名。
- 自動改 UID。
- 自動改推薦人。
- 自動改 owner。

## 儲存規則

儲存前必須檢查：

- label 不可空白。
- value 不可空白。
- type 與 value 必須一致。
- URL scheme 必須安全。
- 電話與 email 格式必須通過。

若不通過：

- 不得儲存。
- 必須顯示明確錯誤。
- 錯誤訊息應指出是哪個按鈕、哪個欄位。

## 推播與網頁版

推播 Flex 與網頁版必須使用同一份按鈕資料。

禁止：

- 編輯頁顯示一套按鈕，推播用另一套預設按鈕。
- 網頁版缺少按鈕。
- 分享後按鈕變成預設值。

## 測試要求

### 掃描通訊錄名片的完整聯絡資料

- OCR 核對後儲存時，依實際非空欄位建立手機、公司電話、Email、網站、地址及社群按鈕，不補入預設電話或平台連結。
- 通訊錄名片不可沿用本人名片的四按鈕上限；編輯、儲存及前端分享均須保留全部有效聯絡按鈕。
- 舊通訊錄名片尚未設定 buttons 時，從已儲存欄位產生完整按鈕；已設定的陣列（包括刪光後的空陣列）以使用者設定為準，不自動補回。
- 不變更本人名片的按鈕上限、UID、歸屬、點數及正式資料。無辨識到的內容不可捏造。

每次改按鈕功能前，至少檢查：

- 電話自動加 `tel:`。
- email 自動加 `mailto:`。
- 錯誤 URL 不可儲存。
- 編輯頁、推播、網頁版按鈕一致。
- 不同版型不會互相覆蓋按鈕。
