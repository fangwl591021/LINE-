# 點數彈窗等待改善

- 使用者回報約 4 秒停在更新點數中。程式證據：每次 fetchPointWalletData_(true) 呼叫完整 queryUserPoints，後端可能抓取 gift_money 與所有類型的多頁明細；QR 模組原先在查詢完成後才載入。
- web-perf / Chrome DevTools 本機 trace 注入 4,000ms 查詢延遲，已有本人有效資料時原版 QR 仍等 4,025ms。這不是使用者正式帳號的實際網路延遲量測。
- 僅前端改善：本人已確認、全域 ready、合法 canonical UID、有限餘額且載入時間在過去 60 秒內才先顯示，標示上次確認／背景更新中；正式完整查詢不變。QR 模組與查詢平行載入。
- 更新失敗保留的已確認預覽必須明確標示更新失敗、上次確認點數；無有效快取時不顯示假零或不明 QR。超時、跨帳號、離頁、關閉後回應規則維持。
- 沒有快取的第一次仍須等待權威查詢，不宣稱正式站已消除所有 4 秒等待。未改後端、扣點流程；使用者於 2026-09-11 授權提交與 GitHub Pages 前端部署，正式結果以 Actions 與上線檔案核對為準。
- 同樣注入 4 秒延遲，390px 首次 QR 出現 25ms、背景確認 4021ms；320px 為 12ms、4030ms。只代表本機已載入彈窗模組、有有效本人快取的情境，不能當成正式端到端網路數據。
- 320/390px 的快取時效、未來時間戳、跨帳號、錯誤資料、背景更新失敗、關閉／切頁等測試通過；完整合約與 38 項商城／收銀回歸通過。
- DevTools trace 記錄在本機 wallet-popup-before.trace.json.gz、wallet-popup-after.trace.json.gz。此次量測為彈窗互動，不以頁面 LCP 或自動切頁產生的 CLS 當作真實使用者效能結論。
