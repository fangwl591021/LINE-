# 核心不變規則

本文件定義本專案不可被任何功能修改破壞的底層規則。若新功能、修補或退版與本文件衝突，應先更新規格並確認風險，不可直接改程式。

## 1. 身分與歸屬

- LINE UID 是會員身分的主要識別鍵。
- 一個 LINE UID 只能對應一張本人「個人專屬名片」。
- 同一個人可有多種名片呈現版本，但不可建立多張互相競爭的本人名片。
- 掃描、OCR、AI名片夾建立的名片預設是「通訊錄名片」，不是掃描者本人的個人名片。
- 通訊錄名片必須記錄原始掃描者或建立者，例如 `scannedBy`、`createdBy` 或等價欄位。
- 邀請加入、推薦好友、QR 或分享連結建立的會員關係必須保留推薦人 UID。
- 沒有推薦人 UID 時，資料可歸入 `admin`，但必須在後台或稽核資料中標記為「無推薦人 / admin fallback」。

## 2. 名片資料邊界

- 本人名片與 AI名片夾通訊錄名片必須分開判斷。
- 我的名片只能讀取目前登入 UID 的本人名片。
- AI名片夾只能列出目前登入 UID 掃描或上傳建立的通訊錄名片。
- 從 AI名片夾掃入的名片，若被原名片本人認領，歸屬可綁定本人 UID，但掃描紀錄仍不得消失。
- 若某張通訊錄名片已被其他 UID 綁定，本人再掃描時只能保留為通訊錄紀錄，不可搶走歸屬權。
- 名片列表不可用姓名、電話或公司名稱直接覆蓋 UID 歸屬。

## 3. 名片版本規則

一張本人名片最多有四種呈現版本：

- 標準版
- 滿版 / 海報版
- 正方版
- 影音版

規則：

- 四種版本必須共用同一個本人 UID。
- 四種版本可以共用基本資料，例如姓名、電話、公司、服務說明。
- 四種版本的封面圖、裁切設定、影片網址、縮圖與版型設定必須互相獨立。
- 影音版不可覆蓋標準版、滿版或正方版的封面圖。
- 關鍵字「我的名片」只應顯示靜態名片版本。
- 關鍵字「影音名片」才應顯示影音版。
- 編輯器進入時必須使用名片版本 resolver 判斷目前要編輯的版本，不可用最後一次寫入資料猜測。

## 4. 公開池與配對

- 自己掃入的通訊錄名片是個人資產，預設不可進入公開 AI 配對池。
- 本人名片完成編修後，可以進入公開交流池。
- 進入公開交流池前，必須通過必要檢查：圖片、標題、說明、按鈕資料有效。
- 未完成編修、未公開或未通過 AI 體檢的名片不可被跨店搜尋或配對。
- 我的名片池與公開交流池必須分開查詢。

## 5. 點數與交易

- 點數異動必須以交易紀錄或 ledger 為準。
- 前端顯示的點數不得直接作為最終真實值。
- 發訊與優惠券交易點數統一扣 10 點。
- 店家消費折抵應使用手動輸入折抵點數，不應固定 10%。
- 所有扣點、贈點、折抵都必須記錄操作者、對象、原因與時間。
- 母站與子站點數必須合併同一個 LINE UID 帳本，不可各自顯示矛盾餘額。

## 6. LINE / LIFF 行為

- Flex 分享按鈕若目標是轉發名片，應直接進入分享流程，不應先跑首頁。
- 需要 `shareTargetPicker()` 的流程必須在具備正確 LIFF scope 的 LIFF URL 中執行。
- 一般網頁版名片應可在瀏覽器開啟，但不能假裝可以呼叫 LINE-only API。
- LINE OA 聊天室關鍵字流程不可要求過度驗證；能從 webhook 取得 source userId 時，應以該 UID 作為流程依據。
- 新用戶首次進入系統不應強制跳註冊頁，應停在首頁並引導建立名片。

## 7. 儲存與驗證

- 電話按鈕 URL 必須是 `tel:` 格式。
- Email 按鈕 URL 必須是 `mailto:` 格式。
- 一般網址必須是可解析的 `http://` 或 `https://` URL。
- LINE 連結必須符合實際可開啟格式。
- 規格不合法時不得儲存，應提示錯誤或提供修正後結果給使用者確認。
- 自動修正不得靜默改寫關鍵資料，例如 UID、推薦人、歸屬網。

## 8. 發版規則

- 涉及 UID、名片歸屬、名片版本、點數、webhook、LIFF scope 的修改都屬高風險。
- 高風險修改必須先對照本文件與回歸測試矩陣。
- 若只要求修補某一流程，不得順手重構其他流程。
- 上線前必須確認目前改動是否會影響：
  - 我的名片
  - AI名片夾
  - 影音名片
  - 推薦好友
  - 點數
  - 收件匣
  - 跟進
  - 後台 CRM
